# 技能结构

本文档描述 zflow 技能文件的结构和格式。在贡献新技能或理解现有技能时，将此作为指南。

## 文件位置

每个技能位于 `skills/` 下自己的目录中：

```
skills/
  skill-name/
    SKILL.md           # 必需：技能定义
    scripts/           # 可选：技能工作流使用的可运行辅助脚本
    supporting-file.md # 可选：按需加载的参考资料
```

`SKILL.md` 是唯一必需的文件。仅当技能确实包含可运行辅助脚本时才添加 `scripts/`，对纯 Markdown 技能则完全省略该目录。

## SKILL.md 格式

### 前置元数据（必需）

```yaml
---
name: skill-name-with-hyphens
description: 引导智能体完成[任务/工作流]。在[特定触发条件]时使用。
---
```

**规则：**
- `name`：小写，用连字符分隔。必须与目录名匹配。
- `description`：以第三人称说明技能功能开头，然后包含一个或多个清晰的"Use when"触发条件。同时包含*做什么*和*何时做*。最多 1024 个字符。

**为什么这很重要：** 智能体通过阅读描述来发现技能。描述会被注入到系统提示词中，因此它必须告诉智能体该技能提供什么以及何时激活。不要总结工作流——如果描述包含流程步骤，智能体可能会遵循摘要而非阅读完整技能。

### 标准章节（推荐模式）

上述前置元数据约定是必需的。下面的章节布局是推荐模式，而非刚性模板：在清晰服务于相同目的时，等效标题是可接受的。

```markdown
# 技能标题

## 概述
用一两句话解释该技能做什么以及为什么重要。

## 何时使用
- 列出触发条件的项目符号（症状、任务类型）
- 何时不使用（排除情况）

## [核心流程 / 工作流 / 步骤]
主要工作流，分解为编号步骤或阶段。
在有帮助的地方包含代码示例。
在存在决策点时使用流程图（ASCII）。

## [具体技术 / 模式]
针对特定场景的详细指导。
代码示例、模板、配置。

## 常见合理化借口
| 合理化借口 | 现实 |
|---|---|
| 智能体用来跳过步骤的借口 | 为什么该借口是错误的 |

## 危险信号
- 表明技能被违反的行为模式
- 审查期间需要注意的事项

## 验证
完成技能流程后，确认：
- [ ] 退出标准检查清单
- [ ] 证据要求
```

## 各章节目的

### 概述
技能的"电梯演讲"。应回答：该技能做什么，智能体为什么应该遵循它？

### 何时使用
帮助智能体和人类决定此技能是否适用于当前任务。包括正向触发条件（"当 X 时使用"）和负向排除条件（"不适用于 Y"）。

### 核心流程
技能的核心。这是智能体遵循的逐步工作流。必须具体且可操作——不是模糊的建议。

**好的示例：** "运行 `go test ./... -race` 并验证所有测试通过"
**差的示例：** "确保测试能用"

### 常见合理化借口
精心编写技能的最显著特征。这些是智能体用来跳过重要步骤的借口，配以反驳。它们防止智能体理性化地逃避遵循流程。

回想一下每次智能体说过"我稍后加测试"或"这太简单了，可以跳过规范"——这些都放在这里，附带事实性的反驳。

### 危险信号
可观察的技能被违反的迹象。在代码审查和自我监控中很有用。

### 验证
退出标准。智能体用来确认技能流程已完成的检查清单。每个复选框都应可通过证据验证（测试输出、构建结果、截图等）。

## 支持文件

仅在以下情况下创建支持文件：
- 参考资料超过 100 行（保持主 `SKILL.md` 专注）
- 需要代码工具或脚本
- 检查清单足够长，值得独立成文件

当低于 50 行时，保持模式和原则内联。

如果技能不需要可运行辅助脚本，不要仅仅为了镜像其他技能而创建空的 `scripts/` 目录。空目录只会增加噪音，而不改变技能的工作方式。

## 共享参考资料

被多个技能使用的检查清单——测试、安全性、性能、可观测性、完成的定义——位于仓库根目录的 `references/` 中，刻意*不*放在任何技能目录内。

这是一个技能包级别的设计选择。zflow 规范将技能描述为自包含的目录，但这里的几个技能指向相同的检查清单。将它们放在一起将迫使在两个选项中二选一：将检查清单复制到每个使用它的技能中，或选择一个技能来"拥有"它并让其他技能访问该目录。两种方式都会随时间推移而偏离。一个单一的仓库根副本保持为事实来源。

权衡取舍是可移植性：整个仓库的安装（如 Claude Code marketplace 插件）会携带 `references/`，但只复制 `skills/<name>/` 的按技能安装会将仓库根的兄弟文件夹落下，那些链接将解析为空。该缺口在 [#361](https://github.com/13eholder/zflow/issues/361) 中被跟踪。

当前约定：被恰好一个技能使用的材料是该技能目录内的支持文件；跨技能共享的材料放在 `references/`。

## 上下文效率

技能按需加载：启动时只有技能名称和描述位于上下文中。完整的 `SKILL.md` 仅在智能体判断该技能相关时才加载。为了保持加载成本低廉：

- **将 `SKILL.md` 保持在 500 行以内。** 将详细的参考资料移入支持文件。
- **编写具体的描述。** 精确的描述帮助智能体在正确的时刻激活技能，否则跳过它。
- **使用渐进式披露。** 引用支持文件，这些文件仅在工作流到达时才被阅读。
- **优先使用脚本而非内联代码。** 执行脚本不消耗上下文；只有其输出消耗。内联代码块在每次加载时都有成本。
- **将文件引用保持在一层深度。** 直接从 `SKILL.md` 链接到支持文件，而非通过中间文档串联。

## 脚本要求

当技能在 `scripts/` 下包含可运行辅助脚本时，每个脚本遵循以下约定：

- 使用 `#!/bin/bash` shebang。
- 使用 `set -e` 实现失败即停止行为。
- 将状态消息写入 stderr：`echo "Message" >&2`。
- 将机器可读输出（JSON）写入 stdout。
- 包含针对临时文件的清理 trap。
- 将脚本路径引用为 `skills/<skill-name>/scripts/<script>.sh`（相对于仓库）。

## 编写原则

1. **流程优于知识。** 技能是工作流，不是参考文档。是步骤，不是事实。
2. **具体优于笼统。** "运行 `go test ./... -race`"胜于"验证测试"。
3. **证据优于假设。** 每个验证复选框都需要证明。
4. **反合理化。** 每个值得跳过的步骤都需要在合理化借口表格中有反驳。
5. **渐进式披露。** 主 `SKILL.md` 是入口。支持文件仅在需要时加载。
6. **Token 意识。** 每个章节都必须证明其存在的必要性。如果删除它不会改变智能体行为，就删除它。

## 命名约定

- 技能目录：`lowercase-hyphen-separated`
- 技能文件：`SKILL.md`（始终大写）
- 支持文件：`lowercase-hyphen-separated.md`
- 参考资料：存储在项目根目录的 `references/` 中，而非技能目录内（原因参见[共享参考资料](#共享参考资料)）

## 跨技能引用

通过名称引用其他技能：

```markdown
编写测试时遵循 `test-driven-development` 技能。
如果构建失败，使用 `debugging-and-error-recovery` 技能。
```

不要在技能间重复内容——应引用和链接。

## 必需 vs 推荐

必需：

- 一个 `skills/<skill-name>/SKILL.md` 文件
- 包含 `name` 和 `description` 的有效 YAML 前置元数据
- 包含技能功能和何时使用的描述

推荐：

- 上面展示的标准章节流程
- 在更自然时使用等效标题，如 `How It Works`、`Core Process` 或 `Workflow`
- 仅在有助于保持主 `SKILL.md` 专注时使用支持文件
