# 采纳指南：按缺口引入，而非按生命周期堆叠

zflow 的目标不是接管智能体的完整开发流程，而是在模型原生能力之外提供少数高价值约束。无论是新项目还是已有代码库，都从真实缺口出发，只加载当前任务需要的技能。

关于安装方式，参见 [getting-started.md](getting-started.md)；完整目录见 [README](../README.md#全部-14-个技能)。

## 共同基线

先把下列内容写进项目自身的规则文件，而不是技能：

- 构建、测试、lint 和格式化命令
- 目录边界与代码所有权
- 安全限制和需要先询问的操作
- 项目特有约定与已知风险区域

智能体原生负责探索代码库、制定临时计划、实现、运行测试、定位失败、检查 diff 和使用 Git。不要为这些常规动作永久加载额外工作流。

## 选择技能的判定

| 发现的缺口 | 引入的技能 |
|------------|------------|
| 公共接口兼容性和错误语义经常遗漏 | `api-and-interface-design` |
| 故障条件下的数据承诺缺少证据 | `consistency-and-durability-verification` |
| 容错只测试正常路径 | `failure-injection-testing` |
| 性能讨论没有基线和可复现实验 | `performance-optimization` |
| 值班人员无法从遥测回答关键问题 | `observability-and-instrumentation` |
| 旧接口或数据结构长期无法下线 | `deprecation-and-migration` |
| 发布缺少灰度、容量或回滚条件 | `shipping-and-launch` |
| 架构决策没有可追溯记录 | `documentation-and-adrs` |
| 框架决策依赖记忆而非当前官方资料 | `source-driven-development` |
| 团队明确需要可评审规范 | `spec-driven-development` |
| 团队明确需要持久化实施计划 | `planning-and-task-breakdown` |
| 可写实现任务委派后经常偏离具体 Stage 的既定架构或模块职责 | `delegated-task-contract` |
| 一轮工作需要跨产物归档 | `stage` |
| 代码可运行但复杂难读，且需要保持行为不变地简化 | `code-simplification` |

没有命中这些缺口时，不加载技能。

## 新项目

新项目通常只需要三步：

1. 在项目规则中写明真实命令和边界。
2. 如果需求复杂且需要团队确认，使用 `/spec`；如果还需要持久化任务清单，再使用 `/plan`。
3. 直接让智能体实现并验证。首次生产发布时使用 `/ship`。

随着系统出现真实需求再增加专业技能：

| 时机 | 建议 |
|------|------|
| 第一个公共 API 或节点间协议 | `api-and-interface-design` |
| 第一个有状态复制路径 | 一致性验证与故障注入技能 |
| 第一次生产部署 | 可观测性与发布技能 |
| 出现明确性能目标 | 性能优化技能 |
| 第一次破坏性演进 | 废弃与迁移技能 |

不要从第一天把 14 个技能全部放进持久上下文。技能描述可以被平台发现，正文只在明确匹配时加载。

## 已有代码库

已有代码库优先保护现状：

1. 先读取项目规则、构建配置、测试和相邻实现，确认实际约定。
2. 修改未覆盖区域前编写特征化测试，固定当前可观察行为。
3. 保持变更小而可回滚，运行受影响测试和全局必要关卡。
4. 仅对接口、数据承诺、故障路径、性能或上线等专业问题加载对应技能。

推荐的渐进顺序：

- 先用 `documentation-and-adrs` 记录必须保留的架构决策。
- 在新旧代码边界使用 `api-and-interface-design` 明确兼容契约。
- 对实际发生过的数据事故使用一致性验证和故障注入技能固化证据。
- 使用 `deprecation-and-migration` 缩小遗留面，而不是长期叠加兼容分支。
- 沿真实值班路径补充 `observability-and-instrumentation`。

## 反模式

- **自动串联多个技能。** 每个技能会重复探索、规划和验证，增加成本并制造冲突。选一个主技能，只有明确缺口时才补充第二个。
- **把文档产物设为所有任务的硬前置。** 小修复不需要规范或长期计划；只有用户或团队需要持久化产物时才创建。
- **把完整技能正文放进全局规则。** 只保留项目约定，技能正文按需加载。
- **用技能替代仓库证据。** 任何工作流都不能替代真实代码、测试输出、指标和官方资料。
- **在未测试的遗留代码上做大规模重写。** 先建立行为基线，再分步修改。

## 采纳成功的信号

- 普通任务不会触发技能。
- 专业任务通常只触发一个边界清晰的技能。
- 规范、计划和 ADR 只在确有协作价值时产生。
- 发布和迁移具有可执行的回滚条件。
- 技能减少遗漏，而不是增加重复步骤。
