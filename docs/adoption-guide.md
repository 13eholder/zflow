# 采纳指南：新项目 vs. 已有代码库

如何推广 zflow 很大程度上取决于你的代码库处于其生命周期的哪个阶段。一个全新项目可以从第一次提交开始就采纳完整的生命周期。一个有多年历史的代码库需要一条渐进式的路径，尊重已存在的一切——其约定、其未记录的决策，以及那些你不希望盲目触碰的缺少测试覆盖的区域。

本指南涵盖两条路径。关于安装机制，参见 [getting-started.md](getting-started.md) 和各工具的设置指南。关于每个技能的功能，参见 [README 中的技能目录](../README.md#全部-24-个技能)。

---

## 你属于哪条路径？

| 信号 | 全新项目 | 已有代码库 |
| -------------------------- | ------------------------------- | -------------------------------------------- |
| 代码库年龄 | 几天到几周 | 几个月到几年 |
| 测试覆盖率 | 你从第一天起掌控 | 不均匀；某些区域未经测试 |
| 约定 | 随开发定义 | 已建立，通常未记录 |
| 团队习惯 | 正在形成 | 根深蒂固（无论好坏） |
| 智能体变更出问题的风险 | 影响范围小 | 可能破坏没人记得如何修复的东西 |
| 采纳策略 | **立即完整生命周期** | **渐进式，验证优先** |

如果你处于两者之间（一个已经发布到生产环境的年轻项目），从已有代码库路径开始并加速，它会收敛到相同的最终状态。

---

## 路径 A | 全新项目：从第一天开始的完整生命周期

新项目是最佳情况：没有遗留行为需要保留，因此技能的质量关卡几乎没有成本，并从第一次提交开始就持续累积收益。

### 第 0 天 | 安装和配置

1. 安装技能包（`npx skills add 13eholder/zflow`，或你所用工具的原生集成，参见 [getting-started.md](getting-started.md)）。
2. 加载 `using-agent-skills`（元技能），使智能体能够自行将工作路由到正确的技能。
3. 添加一个简短的项目规则文件（`CLAUDE.md`、`.cursorrules` 等），包含你的技术栈、命令和边界；`context-engineering` 描述了应该放什么内容。

### 第 0 天 | 在构建之前先定义

为项目的第一个真正功能按顺序运行生命周期：

```
/spec   →  SPEC.md            (spec-driven-development)
/plan   →  tasks/plan.md      (planning-and-task-breakdown)
/build  →  一次一个切片        (incremental-implementation + test-driven-development)
/review →  每次合并前          (code-review-and-quality)
/ship   →  即将上线时          (shipping-and-launch)
```

`/build auto` 非常适合全新项目：你只需批准计划一次，每个任务仍然以测试驱动方式运行并单独提交。规范和计划产物（`SPEC.md`、`tasks/`）是活动文档，在工作进行中保持它们的版本控制。

### 从一开始就将以下视为始终启用

- **test-driven-development**，覆盖率负债在为零时最容易避免。
- **git-workflow-and-versioning**，原子提交和约 100 行的变更是习惯而非后期改造。
- **documentation-and-adrs**，最初的架构决策正是两年后没人会记得*为什么*的那些决策。现在写一份 ADR 可以避免路径 B 中描述的已有代码库考古学。

### 随项目增长逐步添加

| 时机 | 加载 |
| ----------------------------------- | ------------------------------------------------------------- |
| 第一个公共 API 或模块边界 | `api-and-interface-design` |
| 第一条 CI 流水线 | `ci-cd-and-automation` |
| 第一次生产部署 | `observability-and-instrumentation`、`shipping-and-launch` |
| 出现性能要求 | `performance-optimization` |

### 全新项目反模式

- **跳过 `/spec`，因为"这只是一个原型。"** 原型会变成产品。规范是你为这个代码库写过的最便宜的产物。
- **在每个会话中加载全部 24 个技能。** 这会浪费上下文并稀释真正重要的技能。按阶段加载；让 `using-agent-skills` 进行路由。
- **将可观测性推迟到"有东西可以观测时"。** 边构建边埋点；事后改造结构化日志是你选择为自己创造的路径 B 问题。

## 路径 B | 已有代码库：渐进式，验证优先

在已有代码库中，风险特征正好相反：危险不来自于构建错误的东西，而来自于*变更*某些行为没有被完全规定的东西。因此，采纳顺序应从**读取和保护**代码库的技能开始，之后再转向**修改**代码库的技能。

### 阶段 1 | 上下文和只读技能

目标：智能体在修改任何东西之前先理解代码库。

1. **首先加载 `context-engineering`。** 编写项目规则文件，描述真实的约定——代码中的约定，而非 wiki 中的约定。包括构建/测试命令、目录含义、已知雷区（"不要碰 `legacy/billing`，它没有测试，有三个已知的变通方案"）。
2. **对 incoming 变更使用 `code-review-and-quality`。** 审查是零风险的，并且立即有价值：五轴审查及其严重性标签（区分哪些阻止合并——Critical 和 Required——以及哪些不阻止）适用于任何 PR，无论代码库的状态如何。
3. **对你本来就要修复的缺陷使用 `debugging-and-error-recovery`。** 五步排查（复现→定位→缩小→修复→防范）在陌生代码中大放异彩，而"防范"步骤开始构建你缺失的回归测试套件。
4. **将 `doubt-driven-development` 作为安全网。** 遗留代码正是此技能针对的"陌生代码，犯错成本高"场景。对智能体关于遗留系统如何运作的断言进行对抗式全新上下文审查，在它们成为提交之前捕获自信的幻觉。

### 阶段 2 | 变更前先测试

目标：智能体将要触及的每个区域首先获得安全网。

- **有选择地应用 `test-driven-development`。** 不追求全局覆盖率；追求*计划变更区域*的覆盖率。对于未测试的遗留行为，编写特征化测试——在执行任何修改之前确定代码当前行为（无论对错）的测试。Beyonce 规则适用：如果智能体喜欢某个行为到足以依赖它，它就应该对该行为编写测试。
- **在最糟糕的热点区域使用 `code-simplification`。** Chesterton 栅栏是操作原则：该技能强制智能体在移除代码之前理解代码*为什么*存在。保持行为的简化加上特征化测试是使遗留代码变得可修改的最低风险方式。
- **在所有地方使用 `git-workflow-and-versioning`。** 小的原子提交在已有代码库中*更加*重要：当对旧代码的变更破坏了某些微妙的东西时，约 100 行的提交是可二分查找的；2000 行的"现代化"提交则不是。

### 阶段 3 | 新工作运行完整生命周期

目标：双速采纳，遗留代码保持在阶段 1-2 的制度下；**新功能获得全新项目待遇**。

- 在旧代码库中开发新功能？`/spec → /plan → /build → /review`。规范的边界部分是你声明该功能可以触及和不可以触及哪些遗留接口的地方。
- **在接口处使用 `api-and-interface-design`。** 当新代码必须与旧代码对话时，以契约优先设计边界。Hyrum 定律在一个多年的代码库中不是理论——有人依赖每一个可观察的行为，包括缺陷。

### 阶段 4 | 偿还、废弃、观测

- **`deprecation-and-migration`** 是已有代码库场景下最优秀的技能：代码即负债、强制与建议性废弃、僵尸代码清理为你提供了缩小遗留攻击面的纪律化方法，而不是仅仅包装它。
- **`observability-and-instrumentation`** 沿着你实际调试的路径进行改造：首先对最频繁的事件来源进行结构化日志和 RED 指标。
- **`performance-optimization`** 在退化变得重要时使用，其度量优先规则防止了经典的遗留陷阱——优化从未成为瓶颈的代码。

### 已有代码库反模式

- **"大爆炸"式采纳。** 在第一天将完整生命周期加载到遗留代码库上，会为已存在的代码生成规范，并在没有安全网的情况下进行重构。应按顺序进行。
- **让智能体重构未经测试的代码。** 没有特征化测试就没有重构。这是已有代码库采纳中最昂贵的捷径。
- **跳过 `context-engineering`，因为"代码就是文档。"** 智能体会从它碰巧读到的最差文件中推断约定。告诉它真实的约定。
- **默认认为遗留系统的行为是错误的。** Chesterton 栅栏：那个奇怪的重试循环可能承担着关键负载。先理解，再变更。
- **不固化进展。** 采纳应该让质量单调改善：每个阶段增加一个不可回退的关卡。如果一个月后你说不出什么现在是强制执行的而以前不是，说明推广已经停滞。

## 两条路径的汇聚

两者最终的稳态相同：新工作执行 `/spec → /plan → /build → /review → /ship`，始终开启的 TDD 和 git 纪律，合并前审查关卡，按阶段而非批量加载技能。全新项目在几天内到达；已有代码库在一个季度内到达，差异恰好在于旧代码库从未有过的安全网（上下文、特征化测试、边界）。

| | 全新项目 | 已有代码库 |
| ---------------------- | ------------------------------ | ---------------------------------------- |
| 第一个加载的技能 | `using-agent-skills` + `/spec` | `context-engineering` |
| 第一个交付的价值 | 规范化的、已测试的第一个功能 | 零风险审查和更安全的缺陷修复 |
| TDD 态度 | 从第一次提交起通用 | 有选择的：在计划变更区域编写测试 |
| 重构规则 | 罕见（几乎没什么可重构） | 首先编写特征化测试，始终如此 |
| 最危险的反模式 | 跳过规范 | 重构未经测试的代码 |
| 到达完整生命周期的时间 | 第一天 | 约一个季度，期间为双速模式 |
