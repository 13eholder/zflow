# zflow 与其他方案对比

人们经常问 **zflow** 与另外两个他们最常听说的"面向编程智能体的技能"集合——**Superpowers**（Jesse Vincent / obra）和 **Matt Pocock 的技能**——有什么关系。三者都很好，共享大量 DNA，都值得学习。本页面是一份诚实的指南，说明它们是如何被*塑造*得不同的，以便你可以选择适合你工作方式的那个，或者从三个中各自借鉴。

> **要点总结**——它们针对不同的时刻进行了优化。**zflow** 以审查角色、反合理化防护和检查技能实际路由和行为的仓内评估框架来组织*整个产品生命周期*（定义、规划、构建、验证、审查、发布）。**Superpowers** 偏向于*自主、推理密集*的运行，使用子智能体、严格的流水线和工作树隔离。**Matt Pocock 的技能**是一个*犀利、有主见的 Claude Code 工具箱*，提炼自一位专家的日常工作流，带有标志性的"grill me"访谈循环。三者中没有抽象意义上的"最好"；选择取决于你面前的工作。

## 一瞥

| | **zflow** | **Superpowers** | **Matt Pocock 的技能** |
|---|---|---|---|
| **核心理念** | 将完整的资深工程生命周期编码为技能 | 建立在可组合技能之上的完整开发*方法论* | 一位专家的 Claude Code 工作流，开源并持续演进 |
| **组织原则** | 由元技能路由器背后的 SDLC **阶段**（定义到发布） | 一个纪律化的循环：头脑风暴、规划、执行、审查 | 一个精选的、专注的、可组合的命令工具箱 |
| **目录规模** | 覆盖整个生命周期的 24 个技能 | 约 14 个技能，深度聚焦内部构建循环 | 约 30 个技能，分组为工程/生产力/进行中/废弃 |
| **生命周期覆盖** | 广泛：创意精炼、API 和 UI 设计、安全性、性能、CI/CD、可观测性、废弃、ADR、发布 | 深入但较窄：TDD、调试、规划、审查、技能编写 | 定义和构建阶段覆盖深：grilling、PRD、issue、TDD、架构、缺陷分类、知识管理 |
| **入口点** | 与阶段一一映射的斜杠命令（`/spec` `/plan` `/build` `/test` `/review` `/code-simplify` `/ship`），带有 `/build auto` 完整计划模式 | 技能链式流水线（`brainstorming`、`writing-plans`、`subagent-driven-development`） | 斜杠命令（`/grill-me`、`/tdd`、`/to-prd`、`/diagnosing-bugs`、`/grill-with-docs`） |
| **特色机制** | 每个技能中的反合理化表格和危险信号；`/ship` 中的并行审查**角色**；参考资料检查清单；CI 中的**三层评估框架** | 带有任务审查者（规范 + 质量）和修复循环的子智能体驱动开发；git 工作树隔离；编写技能的技能，经过压力测试 | **grilling** 原语（一次一个问题，设计树遍历）；基于接缝的 TDD；明确的用户调用 vs 模型调用分离；issue 跟踪器集成 |
| **质量度量** | 针对整个目录运行触发、路由和行为评估（仓内，部分在 CI 中） | 压力测试方法论是其哲学核心；评估套件现在位于单独的仓库中 | 未随仓库提供评估 |
| **工具覆盖** | Claude Code、Cursor、Gemini CLI、Antigravity、OpenCode、Windsurf、Copilot、Kiro、Codex，加上 `npx skills` CLI | 覆盖面最广且最活跃更新的之一：Claude Code、Codex、Cursor、Copilot CLI、OpenCode、Kimi、Factory Droid、Antigravity、Pi | Claude Code 优先，通过 `npx skills add` 分发；其他智能体在不同保真度下可用 |
| **治理** | 积极审查和合并社区贡献；每个技能都附带评估 | 主要是独立创作；大量未合并的社区 PR | 独立创作、自行合并、公开透明地开发 |
| **最适用于** | 在每个阶段都有人员检查点的情况下驱动一个功能穿越每个阶段 | 长时间、自主、推理密集或探索性工作 | 务实、久经考验的日常工作循环，在需求和 TDD 方面最强 |

*（我们有意省略了 star 数和采纳数字：它们在不同博客中被引用的方式差异很大，而且每周都在变化。三个都在被积极使用和维护。）*

## 三个项目，各自的特点

### Superpowers（obra）

一个建立在可组合技能之上的完整软件开发*方法论*。它押注于**自主性和前期推理**。会话运行一个刻意线性的流水线：苏格拉底式头脑风暴，写出带有日期的规范，只允许一次交接；详细的计划被写成可由"一个热情但品味差且没有上下文的初级工程师"执行的程度；然后子智能体驱动执行，一个全新的子智能体实现每个任务，任务审查者在关闭任务之前对规范合规性和代码质量进行签字，对于标记出的任何问题都有修复循环，最后在最强模型上进行全分支审查。Git 工作树保持并行工作隔离，其 `writing-skills` 技能将 TDD 应用于文档本身：没有技能在没有失败测试的情况下发布。

其优势是真实的：交出一个相当大的任务块，回来看到一个经过审查的结果，具有防止智能体理性化逃避流程的强大护栏。权衡取舍正是这种纪律性的另一面。覆盖范围较窄（它是内部构建循环的方法论，而非安全到发布的整个生命周期），单一流水线在小型变更上可能显得笨重，而最近的方向是降低这种成本，例如合并为单一任务审查者，速度大约翻倍，Token 减半。其社区呼声最高的需求——多智能体团队执行——尚未在盒子里。

**仓库：** <https://github.com/obra/superpowers>

### Matt Pocock 的技能

Matt 开源了他实际使用的 Claude Code 技能，该集合已成长为一个广泛的、有主见的工具箱，公开组织，包含可见的 `in-progress/` 和 `deprecated/` 目录，示范了这些技能所倡导的纪律性。重心不是 TDD，而是**grilling**：一个可复用的访谈循环，每次问一个问题，遍历设计树的每个分支，按顺序解决依赖关系，每个问题提供一个推荐答案，更倾向于阅读代码库而非提问，并在你确认达成共识之前拒绝继续。`grill-me` 和 `grill-with-docs` 是对它的薄包装。TDD 技能也很有特色，愉快地异端（"重构不属于循环的一部分"，它属于代码审查），并且有明确的用户调用与模型调用技能的分离，将智能体上下文视为稀缺预算。

其优势在于真实性和犀利：这是一位非常优秀的工程师发布产品的方式，而不是某委员会设想的框架，需求访谈循环确实非常出色。权衡取舍：在实践中以 Claude Code 为先（其他智能体存在可靠性的边缘问题），没有仓内评估来捕获回归，构建阶段之后的生命周期覆盖较少，部分技能耦合到个人设置向导和跟踪器约定。最近的工作正在从单会话技能向通过 issue 跟踪器的多会话编排推进（进行中的 `wayfinder`）。

**仓库：** <https://github.com/mattpocock/skills> · 相关：<https://github.com/mattpocock/agent-rules-books>

### zflow（本项目）

agent-skills 将**整个产品生命周期**组织为技能，用一个元技能（`using-agent-skills`）将任务路由到正确的技能。每个技能都带有一个**常见合理化借口**表格（智能体为跳过步骤找的借口，每个都有反驳）和**危险信号**。斜杠命令与生命周期阶段一一映射；`/build auto` 在一次通过中运行整个已批准的计划；`/ship` 并行发散审查**角色**（`code-reviewer`、`test-engineer`），然后将它们合并为 go/no-go。它在每个阶段保持人员检查点，附带五个参考资料检查清单，包括完成的定义，并通过大多数主流智能体工具的单命令安装运行。

更新的差异化特性是：一个**三层评估框架**存在于仓库中。第一层检查结构，第二层检查每个技能描述是否包含用户实际使用的词汇，并确保没有两个技能在路由上冲突（确定性的，在 CI 中运行），第三层根据每个技能的期望对智能体的实际执行轨迹进行评分。另外两个项目今天都没有提供这种仓内的、目录范围的度量。相反方向诚实的权衡：zflow 没有像 Superpowers 那样单一的、有主见的"运行"，而三者中没有一个真正很好地解决了持久的跨会话记忆问题。

## 真正的正面交锋：Superpowers vs. zflow

Om Mishra 进行了一次受控实验，相同的模型、相同的仓库、相同的提示词，在 Claude Code 中仅改变技能框架，并撰写了报告：

**["Superpowers vs Agent-Skills: Faster Shipping, Safer Reasoning"](https://www.linkedin.com/pulse/superpowers-vs-agent-skills-faster-shipping-safer-reasoning-om-mishra-dzakf/)** 作者 Om Mishra

公正地总结：

- **zflow** 更快进入编码（约 8 分钟 vs 约 12 分钟）并运行了**更多验证轮次**（7 vs 5，包括完整的测试套件）。更广泛的验证在即时功能之外捕获了一个兼容性问题，而功能特定的测试遗漏了它。他在该任务的**验证深度**上给予了它优势。
- **Superpowers** 投入了更多的**前期架构推理**，他仍然偏好将其作为日常驱动程序，用于演进生产系统和没有既定模式可循的探索性工作。
- Token 效率几乎相同；两者都重新规划了一次。

这是一个开发者的单任务实验，不是基准测试，但它是核心权衡的具体说明：**广泛纪律性验证 vs. 重前期推理**。他自己的结论是诚实的：为任务选择工具。

## 如何决定使用什么

一瞥表格告诉你它们是如何塑造的。以下是如何在实践中选择。

### 从你工作的形态出发

- **一个完整的功能，从前到后？** zflow。它是三个中唯一一个在每个阶段都有检查点，带你从规范经历安全性、性能和发布的过程，所以没有任何东西会悄悄跳过审查或起飞前检查。
- **一个大的、模糊的任务块，你想交出去然后走开？** Superpowers。其流水线和子智能体审查被构建为长时间运行，并返回一个已经对照规范审查过的结果。
- **一个快速、专注的日常循环，特别是在编写代码之前确保需求正确？** Matt Pocock 的技能。grilling 循环是三者中最锋利的需求工具，工具箱不碍事。

### 然后权衡你真正关心的

- **覆盖广度**（安全性、性能、CI/CD、可观测性、发布）：zflow 是明确的选择；其他两者聚焦于内部循环。
- **长时间运行中的自主性**：Superpowers，有意为之。
- **小型变更的低仪式感**：Pocock 的工具箱最轻量；zflow 提供中间档位（小型变更可以直接跳到 `/test` 和 `/review`）；Superpowers 流程最重。
- **对技能本身有效的信心**：zflow 是唯一具有仓库内目录范围评估的，因此描述或路由回归会在 CI 中失败，而不是在之后以神秘的"为什么技能没触发"浮现。
- **需求访谈**：Pocock 的 grilling 是参考实现；zflow 的 `interview-me` 精神上接近，并正在获得一个可选的协作模式。
- **平台覆盖**：zflow 和 Superpowers 几乎到处都能运行；Pocock 在 Claude Code 上最愉快。
- **每个步骤都有人把关 vs. 放手运行**：zflow 默认有检查点；Superpowers 故意最小化运行中的检查点。

### 具体场景

- *"发布一个带有认证、测试和合并前安全审查的新端点。"* zflow：`/spec` 到 `/ship`，最后 test-engineer 角色发散运行。
- *"过夜重构一个棘手的子系统，早上审查。"* Superpowers：交给它计划，让子智能体驱动开发和任务审查者运行。
- *"我有一个模糊的想法，总是让智能体猜测需求。"* Pocock 的 `grill-me`（或 zflow 的 `interview-me`）在任何代码之前确定意图。
- *"修复一个明确的缺陷，测试先行。"* 三者中任何一个都可以；选择你已经安装的最轻量那个。
- *"标准化一个工程师团队在整个仓库中使用智能体的方式。"* zflow：阶段命令、角色和共享检查清单为团队提供了共同词汇，评估保持自定义技能诚实。
- *"创建我自己的技能并知道它们能正确触发。"* zflow，并借用 Superpowers 的压力测试纪律处理那些不能被合理化的技能。

### 个人 vs. 团队

对于个人开发者，品味和惯性取胜：选择其默认设定与你已有的工作方式匹配的那个，最低仪式感的选项往往是用得最多的。对于团队，考量偏向于共享结构和你可以强制执行的护栏：命名的阶段、审查角色、检查清单和在 CI 中失败的评估是让五个人（及其智能体）汇聚于相同标准而非五个私有工作流的关键。这正是 zflow 为之构建的场景，尽管团队完全可以在其中采纳 Superpowers 的审查纪律或 Pocock 的 grilling 循环。

### 共享的前沿（三者共通）

没有一个真正解决了**持久的跨会话记忆**问题：一个智能体在一个会话中学到的东西很少能干净地带到下一个会话。三者都正在围绕它（学习文件、交接产物、跟踪器支撑的规划地图）。如果这是你的瓶颈，你要知道你在它们今天发布的任何版本的前沿，预期目前需要自己拼接一部分。

## 组合使用

你不必排他性地选择，但组合时要小心。这些是 Markdown 技能，不是运行时，因此挑选*个别*技能效果很好：将 Pocock 的 `grill-me`、Superpowers 的隔离模式或某个特定的检查清单与你的主要设置一起引入。

不能做的是同时将两个作为**活跃路由器**运行。堆叠的元技能在命令名称（`/tdd` 在两个地方定义）上冲突，在路由逻辑上竞争，并引入不同的 TDD 哲学，所以你会得到不可预测的行为而非两者的最佳。选择一个框架作为你的主要路由器，按需从其他两者借用。
