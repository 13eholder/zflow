# zflow 与其他方案对比

zflow、[Superpowers](https://github.com/obra/superpowers) 和 [Matt Pocock 的技能](https://github.com/mattpocock/skills) 都为编程智能体提供可复用指令，但优化目标不同。这里不比较随时间快速变化的 star、版本或技能数量，只比较稳定的设计取向。

## 一览

| 维度 | zflow | Superpowers | Matt Pocock 的技能 |
|------|-------|-------------|--------------------|
| 核心取向 | 少量专业基础设施与文档工作流 | 有主见的端到端开发方法 | 精选的日常开发工具箱 |
| 普通编码 | 交给模型原生工作流 | 由方法论中的流程约束 | 按具体工具和命令选择 |
| 技能触发 | 明确领域或明确产物才加载，默认一个主技能 | 工作通常进入组合流程 | 用户或模型按工具选择 |
| 强项 | API 契约、数据承诺、故障注入、性能、可观测性、迁移、发布 | 长任务、自主执行、任务级隔离与复核 | 需求追问和紧凑的日常工作循环 |
| 文档产物 | 规范、计划、ADR、来源证据与 Stage | 规范和计划是方法论的一部分 | 依具体技能而定 |
| 多角色 | 仅在发布判断中并行审查后合并 | 大量使用子智能体完成和复核任务 | 依具体工作流而定 |
| 仓内评估 | 结构、触发路由和可选行为评估 | 有独立的技能测试方法与生态 | 项目形态更轻 |
| 最适合 | 已有强模型能力，只想补充高代价领域约束的团队 | 希望把较大任务交给严格流程自主完成的用户 | 希望采用专家个人工作方式的用户 |

## zflow 的当前边界

zflow 不再把代码探索、任务拆分、实现、测试、调试、重构、diff 自审和 Git 操作包装为独立技能。这些能力已由现代模型和宿主工具稳定提供，重复包装会增加触发冲突、上下文占用和流程成本。

保留的工作流分为两组：

- **专业基础设施能力：** 公共契约、一致性与持久性、故障注入、性能、可观测性、废弃迁移和生产发布。
- **文档与明确产物：** 工程文档与 ADR、官方来源验证、规范、持久化计划和 Stage。

三个斜杠入口只覆盖明确产物或高风险关卡：`/spec`、`/plan` 和 `/ship`。日常编码直接交给主智能体。

## 如何选择

- 需要一个覆盖完整实现循环、能长时间自主推进的方法论：优先评估 Superpowers。
- 需要强需求访谈或某位专家的具体工作习惯：优先评估 Matt Pocock 的技能。
- 已经信任模型的基础工程能力，只想在基础设施高风险点和文档产物上补齐约束：使用 zflow。

## 组合使用

可以组合，但应避免让多个框架同时接管同一层工作：

1. 选一个方案负责普通开发循环。
2. 仅在专业领域缺口出现时引入 zflow 的对应技能。
3. 对同一请求默认只给一个主技能，避免重复探索、规划和验证。
4. 如果两个技能都适用，明确主次和交接产物，不要建立自动级联。

例如，可以让其他方法论负责实现，而在公共 RPC 设计时单独使用 `api-and-interface-design`，上线前再显式使用 `shipping-and-launch`。

## zflow 的取舍

收益：

- 更少的误触发与上下文开销。
- 技能边界更容易解释和评估。
- 高风险基础设施工作仍有领域化检查点。
- 文档产物具有稳定格式和验证标准。

代价：

- 不提供一条从想法到提交的强制流水线。
- 普通开发质量取决于所用模型、宿主工具和项目规则。
- 想要完全自主的长任务编排时，需要依赖平台原生能力或其他方法论。

## 评估建议

用你自己的仓库和同一个模型做小规模对照，不要只比较目录数量。至少观察：任务完成率、无关技能触发次数、总上下文消耗、验证证据质量、需要人工纠正的次数，以及生产风险是否有可执行的回滚条件。
