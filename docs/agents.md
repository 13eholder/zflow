# 智能体角色

专业角色，每个角色在单一视角下扮演单一职责。每个角色是一个 Markdown 文件，被你的工具框架（Claude Code、Cursor、Copilot 等）作为系统提示词消费。

| 角色 | 职责 | 最适用于 |
|---------|------|----------|
| [code-reviewer](../agents/code-reviewer.md) | 高级 Staff 工程师 | 合并前五轴审查 |
| [test-engineer](../agents/test-engineer.md) | QA 工程师 | 测试策略、覆盖率分析、Prove-It 模式 |

## 角色与技能和斜杠命令的关系

三个层次，各有不同的职责：

| 层次 | 是什么 | 示例 | 组合角色 |
|-------|-----------|---------|------------------|
| **技能** | 带有步骤和退出标准的工作流 | `code-review-and-quality` | *如何做*——从角色或斜杠命令内部调用 |
| **角色** | 具有视角和输出格式的角色 | `code-reviewer` | *谁来做*——采用某种观点，产出报告 |
| **命令** | 面向用户的入口点 | `/review`、`/ship` | *何时做*——组合角色和技能 |

用户（或斜杠命令）是编排者。**角色不调用其他角色。** 技能是角色工作流中的必经跳转。

## 何时使用每种方式

### 直接调用角色
当你想要对当前变更的单一视角评估，并且用户在循环中时选择此方式。

- "审查这个 PR" → 直接调用 `code-reviewer`
- "结账流程缺少哪些测试？" → 直接调用 `test-engineer`

### 斜杠命令（背后是单一角色）
当你有一个可重复的工作流，否则每次都需要重新解释时选择此方式。

- `/review` → 用项目的审查技能包装 `code-reviewer`
- `/test` → 用 TDD 技能包装 `test-engineer`

### 斜杠命令（编排者——发散模式）
仅当**独立**的调查可以并行运行并产生报告，然后由单个智能体合并时选择此方式。

- `/ship` → 并行发散到 `code-reviewer` + `test-engineer`，然后将它们的报告综合为 go/no-go 决策

这是本仓库认可的唯一编排模式。参见 [references/orchestration-patterns.md](../references/orchestration-patterns.md) 了解完整模式目录和反模式。

## 决策矩阵

```
工作是针对单个产物的单一视角评估吗？
├── 是 → 直接调用角色
└── 否 → 子任务是独立的吗（无共享可变状态，无顺序依赖）？
         ├── 是 → 使用并行发散模式的斜杠命令（例如 /ship）
         └── 否 → 由用户运行的顺序斜杠命令（/spec → /plan → /build → /test → /review）
```

## 示例：有效的编排

`/ship` 是本仓库中规范的发散编排者：

```
/ship
  ├── (并行) code-reviewer    → 审查报告
  └── (并行) test-engineer    → 覆盖率报告
                  ↓
        合并阶段（主智能体）
                  ↓
        go/no-go 决策 + 回滚计划
```

为什么这样有效：
- 每个子智能体操作相同的 diff，但产生**不同的视角**
- 它们之间没有依赖关系 → 真正的并行，实际的墙钟时间节省
- 每个子智能体在全新的上下文窗口中运行 → 主会话保持整洁
- 合并步骤很小且受益于完整上下文，因此保留在主智能体中

## 示例：无效的编排（不要构建这个）

一个职责是"决定调用哪个其他角色"的 `meta-orchestrator` 角色：

```
/work-on-pr → meta-orchestrator
                  ↓ (决定"这需要一个审查")
              code-reviewer
                  ↓ (返回)
              meta-orchestrator (转述结果)
                  ↓
              用户
```

为什么这样失败：
- 纯粹的路由层，没有领域价值
- 增加了两次转述跳转 → 信息损失 + 2 倍 Token 成本
- 用户已经知道他们想要审查；让他们直接调用 `/review`
- 复制了斜杠命令和 `AGENTS.md` 意图映射已经完成的工作

## 角色规则

1. 一个角色对应单一的职责和单一的输出格式。如果你发现要添加第二个职责，就创建第二个角色。
2. **角色不调用其他角色。** 组合是斜杠命令或用户的职责。在 Claude Code 上这也是一个硬平台约束——*"子智能体不能生成其他子智能体"*——所以这个规则被平台强制执行。
3. 角色可以调用技能（*如何做*）。
4. 每个角色文件以"组合"块结尾，声明它适用于何处。

## Claude Code 互操作

本仓库中的角色被设计为无需修改即可作为 Claude Code 子智能体和 Agent Teams 团队成员：

- **作为子智能体：** 当此插件启用时自动发现（无需路径配置）。使用 Agent 工具及 `subagent_type: code-reviewer`（或 `test-engineer`）。`/ship` 是规范示例。
- **作为 Agent Teams 团队成员**（实验性，需要 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）：在生成团队成员时按相同角色名称引用。角色的正文被**追加到**团队成员的系统提示词中作为附加指令（不是替换），因此你的角色文本位于主导安装的团队协调指令之上（SendMessage、任务列表工具等）。

子智能体只将结果报告回主智能体。Agent Teams 允许团队成员直接互相通信。当报告就足够时使用子智能体；当子智能体需要质疑彼此的发现时使用 Agent Teams（例如竞争假设调试）。完整映射参见 [references/orchestration-patterns.md](../references/orchestration-patterns.md)。

插件智能体不支持 `hooks`、`mcpServers` 或 `permissionMode` 前置元数据——这些字段会被静默忽略。在编写新角色时避免依赖它们。

## 添加新角色

1. 创建 `agents/<role>.md`，使用与现有角色相同的前置元数据格式。
2. 定义角色、范围、输出格式和规则。
3. 在底部添加**组合**块（何时直接调用 / 通过什么调用 / 不要从另一个角色中调用）。
4. 将角色添加到本文件顶部的表格中。
5. 如果角色启用了新的编排模式，在 `references/orchestration-patterns.md` 中记录该模式，而不是在角色文件本身中发明模式。
