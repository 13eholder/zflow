description: 通过并行发散到专业角色运行发布前检查清单，然后综合出 go/no-go 决策
---

调用 zflow:shipping-and-launch 技能。

`/ship` 是一个**发散编排者**。它并行运行两个专业角色对当前更改进行审查，然后将它们的报告合并为带有回滚计划的单一 go/no-go 决策。角色独立运行——无共享状态，无顺序依赖——这正是并行执行在此处安全且有用的原因。

## 阶段 A——并行发散

使用 Agent 工具并发生成两个子智能体。**在单个助手回合中发出所有两个 Agent 工具调用，以便它们并行执行**——顺序调用违背了此命令的目的。

在 Claude Code 中，每个调用传递与角色 `name` 字段匹配的 `subagent_type`：

1. **`code-reviewer`**——对暂存的更改或最近的提交运行六轴审查（正确性、并发正确性、错误处理、可读性、架构、资源生命周期）。输出标准审查模板。
2. **`test-engineer`**——分析更改的测试覆盖率。识别快乐路径、边界情况、错误路径、并发与故障注入场景中的缺口。输出标准覆盖率分析。

在没有 Agent 工具的其他框架中，顺序调用每个角色的系统提示词，并将它们的输出视为并行返回——合并阶段仍然有效。

约束（来自 Claude Code 的子智能体模型）：
- 子智能体不能生成其他子智能体——不要让一个角色委托给另一个。
- 每个子智能体获得自己的上下文窗口，并仅将其报告返回给主会话。
- 如果你需要相互通信的团队成员而非仅仅报告回来，使用 Claude Code Agent Teams 并将这些角色作为团队成员类型引用（参见 `references/orchestration-patterns.md`）。

**角色解析。** 如果你在 `.claude/agents/` 或 `~/.claude/agents/` 中定义了自己的 `code-reviewer` 或 `test-engineer`，这些会优先于本插件版本——`/ship` 自动拾取你的自定义。这是有意设计的：插件子智能体位于 Claude Code 作用域优先级表的底部，因此用户级定义在设计上胜出。

## 阶段 B——在主上下文中合并

一旦两个报告都回来了，主智能体（而非子角色）综合它们：

1. **代码质量**——汇总来自 `code-reviewer` 的 Critical/Important 发现以及任何失败的测试、lint 或构建输出。
2. **性能**——从 `code-reviewer` 的性能轴提取；交叉检查 p99/p999 延迟与容量水位。
3. **容量与水位线**——验证磁盘/带宽水位、配额限制（两个角色未覆盖——在此直接处理）。
4. **基础设施**——环境变量、迁移、监控、功能开关。直接验证。
5. **文档**——README、ADR、变更日志。直接验证。

## 阶段 C——决策和回滚

产生单一输出：

```markdown
## 发布决策：GO | NO-GO

### 阻塞项（发布前必须修复）
- [来源角色：Critical 发现 + 文件:行号]

### 建议修复（发布前应该修复）
- [来源角色：Important 发现 + 文件:行号]

### 已确认风险（仍要发布）
- [风险 + 缓解措施]

### 回滚计划
- 触发条件：[什么信号会提示回滚]
- 回滚流程：[确切步骤]
- 恢复时间目标：[目标]

### 专业报告（完整）
- [code-reviewer 报告]
- [test-engineer 报告]
```

## 规则

1. 阶段 A 的两个角色并行运行——绝不顺序运行。
2. 角色不互相调用。主智能体在阶段 B 中合并。
3. 在任何 GO 决策之前，回滚计划是强制性的。
4. 如果任何角色返回 Critical 发现，默认判决为 NO-GO，除非用户明确接受风险。
5. **仅在以下所有条件均为真时跳过分发：** 更改涉及 2 个或更少文件，diff 在 50 行以下，且不涉及认证、数据访问或配置/环境变量。否则，默认发散。`/ship` 是为面向生产的更改设计的——当影响范围非平凡时，即使 diff 看起来很小也要运行并行审查。
