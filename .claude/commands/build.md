description: 增量实现任务——构建、测试、验证、提交。添加 "auto" 以在一次批准通过中运行整个计划。
---

调用 zflow:incremental-implementation 技能，同时调用 zflow:test-driven-development。

## 模式

- **`/build`**——实现*下一个*待处理任务，然后停止（仔细，一次一个切片）。
- **`/build auto`**——如果需要则生成计划，获得一次批准，然后实现*每个*任务，任务之间不停止。

`$ARGUMENTS` 选择模式。将 `auto`（规范形式）或 `all` 视为自主模式；其他任何内容（或为空）为默认的单任务模式。注意：自主模式并*不是每个任务更快*——它运行相同的测试驱动循环——它仅去除了任务之间的人工介入。

## 默认：一个任务

从计划中选择下一个待处理任务。然后：

1. 阅读该任务的验收标准
2. 加载相关上下文（现有代码、模式、类型）
3. 为预期行为编写一个失败的测试（RED）
4. 实现使测试通过的最小代码（GREEN）
5. 运行完整的测试套件检查回归
6. 运行构建以验证编译
7. 使用描述性消息提交
8. 将任务标记为完成并停止

## 自主模式：整个计划（`/build auto`）

当规范已存在且你想将规划 + 构建合并为一次运行时使用。它去除了任务之间的手动步进——**而非**验证。每个任务仍然需要通过测试并获得自己的提交。

1. **需要规范。** 仅在已知路径查找规范：仓库根目录的 `SPEC.md`、`docs/SPEC.md` 或 `spec/` 下的文件。README 或任意文档**不算**。如果不存在，停止并告诉用户先运行 `/spec`——不要编造需求。
2. **建立干净基线。** 运行 `git status --porcelain`。如果在预期规划产物（`SPEC.md`、`docs/SPEC.md`、`spec/*`、`tasks/plan.md`、`tasks/todo.md`）之外有未提交的更改，停止并询问用户是提交、暂存还是确认如何处理。自主的按任务提交不能吸收无关的本地工作，否则干净回滚的保证就会失效。
3. **需要时规划。** 如果没有 `tasks/plan.md`，调用 zflow:planning-and-task-breakdown 生成一个。
4. **单一检查点。** 展示完整计划，等待明确的肯定（例如"approve"、"go"、"yes"）。将含糊的回复（"看起来合理"、"我觉得可以"）视为**未**批准。这是唯一的人员关卡——批准后，自主运行。如果你生成了 `tasks/plan.md`，现在将其作为一个预备性提交提交，以免它混入第一个任务的提交中。
5. **按依赖顺序执行每个任务。** 使用每个任务声明的依赖关系；如果它们不明确，按计划列出的顺序执行。对于每个任务，运行上述完整的默认循环（RED → GREEN → 回归 → 构建 → 提交 → 标记完成）。仅暂存该任务触及的文件及任务状态更新——绝不要盲目使用 `git add -A`——并且每个任务做一个提交，这样任何点都是一个干净的回滚点。
6. **停止并询问用户**（不要强行推进）当：
   - 一个测试无法通过或构建在没有明显修复的情况下中断 → 遵循 zflow:debugging-and-error-recovery
   - 规范不明确，或任务需要规范未涵盖的决策
   - 一个任务是高风险或不可逆的——认证/权限变更、破坏性数据迁移、支付、删除、部署、任何涉及密钥的内容，**或任何你无法用 `git revert` 撤销的内容** → 遵循 zflow:doubt-driven-development 并在继续前获得明确批准

   用户解决阻塞后，他们重新调用 `/build auto`——它会从下一个待处理任务恢复。
7. **最后总结：** 已完成的任务、已添加的测试、已做的提交，以及任何被跳过、标记或留给用户的内容。

如果任何步骤失败，遵循 zflow:debugging-and-error-recovery 技能。
