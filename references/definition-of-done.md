# 完成的定义

一个固定的、项目范围内的标准，每个变更在算作完成之前都必须通过此标准。与验收标准不同——验收标准因任务而异，回答"我们构建了正确的东西吗？"——完成的定义每次都一样，回答"这是否符合我们的标准？"。在 `planning-and-task-breakdown`、`incremental-implementation` 和 `shipping-and-launch` 中将其用作最终关卡。

## 完成的定义 vs. 验收标准

| | 验收标准 | 完成的定义 |
|---|---|---|
| 范围 | 特定于一个任务或规范 | 适用于每个增量 |
| 变化 | 每个事项都不同 | 固定且可复用 |
| 回答 | "我们构建了*这个东西*吗？" | "它*准备好了*吗？" |
| 责任人 | 在规划任务时定义 | 为项目一次性定义 |
| 示例 | "用户可以通过邮件链接重置密码" | "测试通过，无回归，文档已更新" |

两者互补。一个任务只有在**其**验收标准**同时**满足固定的完成的定义时才算是完成。跳过任何一项都会留下看起来完成但实际未完成的工作。

## 固定检查清单

对每个变更在宣布完成前应用此清单。

### 正确性
- [ ] 任务的所有验收标准均已满足
- [ ] 代码运行并表现如预期，已在运行时验证，而非仅编译或类型检查
- [ ] 新行为被测试覆盖，这些测试在没有该变更时失败，在有该变更时通过
- [ ] 现有测试仍然通过；未引入回归
- [ ] 边界情况和错误路径已被处理，而不仅仅是快乐路径

### 质量
- [ ] 代码通过命名和结构揭示意图；无需注释来解释它*做了什么*
- [ ] 无重复的业务逻辑
- [ ] 无遗留的死代码、调试输出或注释掉的代码块
- [ ] 变更范围限制在任务内；没有混入无关的重构
- [ ] Linting 和格式化通过

这些项目背后的深度内容见 `code-review-and-quality`（五轴审查）和 `code-simplification`（在不改变行为的情况下降低复杂度）。

### 集成
- [ ] 变更与系统的其余部分协同工作，而不仅仅是孤立运行
- [ ] 数据库迁移、配置变更和功能开关已被考虑
- [ ] 任何公共接口或 API 变更都考虑了向后兼容性

### 文档
- [ ] 公共接口、API 和面向用户的行为已被记录
- [ ] 值得保留的架构决策已被记录（参见 `documentation-and-adrs`）
- [ ] 文档以永恒的语言描述当前状态，而非变更历史

### 发布就绪
- [ ] 新的关键路径已设置可观测性（日志、指标、追踪）（参见 `observability-and-instrumentation`）
- [ ] 任何有风险的内容都存在回滚路径（参见 `shipping-and-launch`）
- [ ] 在合并或部署之前已经人员审查和批准

## 如何应用

- **每个任务**：在勾掉任务之前确认正确性和质量部分。
- **每个功能**：在认为功能完成之前确认集成和文档部分。
- **每次发布**：完整检查清单是最低标准；`shipping-and-launch` 在此基础上添加部署特定的关卡。

为项目定制一次此列表，然后原样复用。一个每个迭代都重新谈判的完成的定义不是一个完成的定义。

## 危险信号

- "完成了，我只是还没有运行过"：未经验证的工作不算完成。
- "测试通过"被用作完成的同义词，而文档、回归测试或运行时验证被跳过。
- 根据截止日期的压力应用不同的标准。
- 验收标准被视为全部标准，没有固定的质量底线。
- 在需要人员审查的变更上，在审查之前就宣布"完成"。
