## 延迟目标

| 指标 | 良好 | 需要改进 | 差 |
|--------|------|------------|------|
| 读延迟 p99（NVMe 本地盘） | ≤ 500µs | ≤ 2ms | > 2ms |
| 写延迟 p99（含持久化） | ≤ 1ms | ≤ 5ms | > 5ms |
| RPC 延迟 p99（同机房） | ≤ 1ms | ≤ 10ms | > 10ms |
| RPC 延迟 p999 | ≤ 10× p99 | ≤ 50× p99 | > 50× p99 |
| 磁盘利用率（util%） | ≤ 70% | ≤ 90% | > 90% |
| 网络吞吐（相对链路带宽） | ≤ 60% | ≤ 80% | > 80% |

原则：**先看 p99/p999，再看平均值**。平均值正常而尾延迟爆炸，是队列堆积、重试风暴或慢盘的典型信号。

## 延迟突刺诊断路径

当 p99 突然升高时，按请求路径自上而下逐层定位，每层先问"是这一层吗"再深入：

- [ ] **客户端/入口层** → 是否有重试风暴？连接池是否打满？超时设置是否导致放大？
- [ ] **服务进程** → CPU 是否饱和（`top`/`mpstat`）？是否有 GC/停顿？锁竞争（`perf` 看 off-CPU）？
- [ ] **网络** → RTT 是否升高（`ping`/`sar -n DEV`）？有重传吗（`ss -i`/`nstat`）？带宽是否打满？
- [ ] **存储** → 磁盘 util% 是否接近 100%（`iostat -x 1`）？await 是否远大于 svctm（队列堆积）？是否存在慢盘（单盘延迟离群）？
- [ ] **对端/下游** → 副本同步、远端节点是否成为瓶颈？

规则：**一次只怀疑一层，用数据排除后再下移**。跳过中间层直接改底层参数，是最常见的无效优化。

## 存储检查清单

### IO 路径
- [ ] 已用 `fio` 建立基准（顺序/随机、读/写、不同块大小、不同队列深度），改动前后对比
- [ ] 队列深度与设备能力匹配（NVMe 深队列，SATA SSD 浅队列；过深只增延迟不增吞吐）
- [ ] 随机小写是否被聚合为顺序写（WAL/LSM 设计目标）
- [ ] 写路径的 fsync/fdatasync 调用点经过审计：每次调用都有明确的持久化语义依据
- [ ] 读写放大已量化（LSM  compaction 放大、RAID/擦除码写放大、全页写）
- [ ] 预读（readahead）设置与访问模式匹配：随机读场景关闭或调小

### 缓存与内存
- [ ] 缓存命中率有监控，且按热度分层（热数据在内存，温数据在 SSD）
- [ ] 淘汰策略与访问模式匹配（LRU 对扫描型负载失效——考虑 LRU-K/ARC/分段 LRU）
- [ ] page cache 与 direct IO 的选择有明确理由，无双倍缓存
- [ ] 大页/huge page 对 TLB 敏感路径（大内存索引、哈希表）已评估

### CPU 与并发
- [ ] IO 线程与 CPU 亲和性（affinity）已配置，避免跨 NUMA 节点访问内存/网卡/磁盘
- [ ] 锁竞争已用 `perf` / off-CPU 分析量化，而非凭猜测加无锁结构
- [ ] 忙轮询（polling）与中断的权衡有数据支撑（SPDK/DPDK 场景）

## 网络检查清单

- [ ] 基准吞吐已测（`iperf3`），并与链路理论带宽对比
- [ ] RTT 基线已测（`ping`/`sockperf`），跨机房/跨可用区单独记录
- [ ] TCP 重传率有监控（`nstat -az | grep -i retrans`），> 0.1% 需要排查
- [ ] 连接建立开销已优化：长连接 + 连接池，避免每请求三次握手 + TLS 握手
- [ ] MTU/分片问题已排除（尤其在 overlay 网络、RDMA 环境）
- [ ] Nagle 与 delayed ACK 的交互已评估：小消息延迟敏感场景设置 `TCP_NODELAY`
- [ ] 网卡队列与中断亲和性（irqbalance / 手动 smp_affinity）与业务线程对齐
- [ ] 无 TCP incast 风险：多对一突发写入场景评估了交换机缓冲与 ECN/DCQCN

## 分布式系统检查清单

- [ ] 超时逐层递减（入口 > 服务 > 下游），且小于上游重试间隔——否则重试放大
- [ ] 重试带指数退避 + 抖动（jitter），且有重试预算上限
- [ ] 无跨节点同步等待链：关键路径上的串行 RPC 已画出并计数（每多一跳 p99 叠加）
- [ ] 批处理/流水线已应用：多次小 RPC 合并为一次（摊薄 RTT 与序列化开销）
- [ ] 热点已排查：分片键是否倾斜（单分片流量/容量离群）、是否有"明星 key"
- [ ] 慢节点有隔离机制（hedged request、慢节点熔断、副本选择避开高延迟节点）
- [ ] 扩容/重均衡期间的性能影响已评估（数据搬迁占用带宽与 IO，需要限速）

## 度量命令

```bash
# === 存储 ===
# fio 随机读基准（4K，队列深度 32，direct IO）
fio --name=randread --rw=randread --bs=4k --iodepth=32 --direct=1 \
    --ioengine=libaio --size=10G --runtime=60 --time_based --group_reporting

# fio 混合读写 + 延迟百分位输出
fio --name=mix --rw=randrw --rwmixread=70 --bs=8k --iodepth=16 \
    --direct=1 --size=10G --percentile_list=50:90:99:99.9

# 实时磁盘指标：重点看 r_await/w_await、aqu-sz（队列长度）、%util
iostat -xz 1

# 块设备 IO 轨迹（谁在发 IO、大小分布、延迟分布）
blktrace -d /dev/nvme0n1 -o - | blkparse -i -
biolatency 10 1        # eBPF：块设备延迟直方图
biosnoop               # eBPF：逐条 IO 的进程与延迟

# === CPU / 锁 / 停顿 ===
perf top                          # 热点函数
perf record -g -p <pid> sleep 30  # 采样 30 秒调用栈
perf sched record -- sleep 10     # 调度延迟
offcputime-bpfcc -p <pid> 10      # off-CPU 时间归因（锁等待/IO 等待）

# === 网络 ===
iperf3 -c <peer> -t 30            # 吞吐基准
ping -c 100 -i 0.01 <peer>        # RTT 基线（注意权限与限速）
sar -n DEV,TCP,ETCP 1             # 吞吐 + 重传 + 主动/被动建连
ss -ti                            # 每条连接的 RTT、重传、拥塞窗口
tcplife                           # eBPF：连接生命周期与字节数
tcpretrans                        # eBPF：重传事件定位

# === 全链路 ===
mpstat -P ALL 1                   # 每核利用率，找单核打满（软中断、单线程瓶颈）
pidstat -d 1                      # 每进程磁盘读写
dstat --top-io --top-latency 1    # 找 IO 大户与延迟大户
```

## 常见反模式

| 反模式 | 影响 | 修复方法 |
|---|---|---|
| 只看平均延迟 | p99 问题被掩盖 | 监控 p50/p99/p999 分层告警 |
| 盲目调大队列深度 | 吞吐不涨、延迟暴涨（Little's Law） | fio 扫描 iodepth，取吞吐拐点 |
| 关键路径串行 RPC | 每跳叠加 p99，尾延迟失控 | 并行化、批处理、流水线 |
| 重试无退避无上限 | 故障期间流量放大，雪崩 | 指数退避 + 抖动 + 重试预算 |
| fsync 过于频繁 | 写吞吐掉到磁盘寻道上限 | 组提交（group commit）、WAL 批量刷盘 |
| 跨 NUMA 访问 | 内存/IO 延迟翻倍且波动大 | CPU 亲和性 + 本地内存分配 |
| 慢盘拖累全池 | 单盘离群拉高整体 p99 | 慢盘检测、隔离、自动下线 |
| 用平均值容量规划 | 峰值时队列爆炸 | 按峰值 + 利用率上限（70%）规划 |
