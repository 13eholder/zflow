## 值班问题（从这里开始）

没有问题导向的遥测数据就是噪音。在添加任何埋点之前：

- [ ] 写下 2-4 个值班工程师会就此组件提出的问题（哪个节点慢？哪块盘在拖后腿？副本落后多少？）
- [ ] 下面的每个信号都映射到这些问题之一
- [ ] 每个问题匹配正确的信号类型：指标说明**有**问题，追踪说明问题在**哪个节点/哪一跳**，日志说明**为什么**

## 结构化日志

- [ ] 日志是结构化的（JSON），具有稳定的事件名称——不是自由格式字符串
- [ ] 每条日志行都带有关联/请求 ID，在请求进入集群的边界生成或接受
- [ ] 每条日志行都带定位三要素：`nodeId`、`shardId`（或 `replicaId`）、设备/接口名
- [ ] 关联 ID 在每次跨节点 RPC 和异步边界上传播（RPC 请求头、复制消息、队列任务元数据）
- [ ] 日志级别一致：`error` = 不变量被打破（数据损坏、一致性校验失败），可能有人需要行动；`warn` = 降级但已处理（切换副本、绕过慢盘）；`info` = 重要集群事件（选举、rebalance、节点进出）；`debug` = 在生产环境中关闭
- [ ] 任何日志行中都没有密钥、Token 或未脱敏的数据负载——遥测管道是经典的数据泄露路径
- [ ] 字段是白名单制的——记录偏移量、长度、校验和，不记录整条 record 或整个 block 的内容
- [ ] 数据面高吞吐路径（每请求/每包）有采样策略；错误、超时和慢操作保留 100%
- [ ] 抽查实际日志输出：结构化字段，不是打印出来的指针地址或 `[object Object]`

## 指标（USE 方法）

对**每一种资源**逐一检查三要素：Utilization（利用率）、Saturation（饱和度）、Errors（错误）：

- [ ] **磁盘**：`util%`、`await` 与队列深度、设备错误/I/O 超时/重试计数（有 SMART 数据更好）
- [ ] **网卡/链路**：吞吐/带宽比、发送队列堆积、TCP 重传率与丢包率、NIC 硬件/CRC 错误
- [ ] **CPU**：利用率（区分 user/sys/iowait/steal）、run queue 长度、节流事件
- [ ] **内存**：用量、swap 换入换出速率、OOM kill 与分配失败
- [ ] 客户端入口面叠加 **RED**：速率（Rate）、错误（Errors）、延迟（Duration）
- [ ] 延迟是直方图；p50/p95/p99/p99.9 可查询——绝不用平均值
- [ ] 所有标签来自小而固定的集合（节点角色、设备类型、分片状态、错误类别）
- [ ] 无无界标签值：没有节点 ID、分片 ID、请求 ID、peer 地址或错误消息文本——per-node 维度由采集端按实例导出，而非标签
- [ ] 副本落后量（lag）、rebalance 进度、后台任务（compaction/GC）耗时均有指标

## 分布式追踪

- [ ] 追踪展示的是请求的物理路径：客户端 → leader → 各副本/分片节点 → 落盘/确认
- [ ] 每个 span 携带定位属性：`nodeId`、`shardId`、`rpcType`、IO span 上的 `diskDevice`
- [ ] 追踪上下文在每次跨节点 RPC 时传播（W3C `traceparent`/`tracestate`），并从每次入站 RPC 中提取
- [ ] 上下文在异步边界上存活——内存队列、后台落盘线程、网络线程、复制消息都携带追踪元数据
- [ ] 存储引擎内部异步路径有手动 span（`appendToLog`、`fsync`、`replicateToFollowers`、`compaction`）
- [ ] 不将密钥或数据负载作为 span 属性
- [ ] 头部采样使用低默认比例；如果有尾部采样可用，保留 100% 的错误和慢请求

## 慢节点/慢盘离群检测

- [ ] 可以按节点查询延迟 p99 的 top-N——而非只看集群平均
- [ ] 可以按设备找出 `await`/`util%` 显著高于同侪的慢盘
- [ ] 副本落后量按节点分布可见——能指出永远追不上的 follower
- [ ] TCP 重传率按节点对（peer）分布可见——能指出丢包的链路
- [ ] 检测到离群点后，已有日志/追踪能回答"为什么是它"，无需从头猜

## 告警

- [ ] 每个告警都基于症状（客户端 p99 超 SLO、读错误率、副本落后持续增长）——原因（CPU、磁盘 util%、重启）放入仪表盘，不放分页器
- [ ] 每个告警都是可操作的；"等 rebalance 完会自愈"的告警被删除
- [ ] 每个告警链接到 runbook——最少三行：它意味着什么、第一个要运行的查询（通常是"找出离群节点/盘"）、升级路径
- [ ] 阈值和持续时间由 SLO 或历史数据证明合理，而非猜测
- [ ] 仅两种严重性：**page**（数据面受损或有数据丢失风险，立即行动）和 **ticket**（容量/冗余降级，本周内行动）
- [ ] 每个新告警试触发一次：它到达了正确的渠道，runbook 链接有效
- [ ] 没有每天触发并被无行动确认的告警

## 仪表盘

- [ ] 存在集群健康仪表盘：客户端错误率、延迟 p99/p99.9、吞吐、各资源饱和度
- [ ] 存在离群面板：按节点/按盘的延迟与错误 top-N
- [ ] 存在副本/分片面板：落后分布、rebalance 进度、后台任务状态
- [ ] 仪表盘回答了此检查清单顶部的值班问题——而不是"除了答案之外的一切"
- [ ] 默认时间范围合理（1 小时到 6 小时，而非 30 天）

## 验证遥测数据

埋点是代码；它可能出错：

- [ ] 在测试集群中注入磁盘故障/节点延迟 → 通过关联 ID 在日志中重建了请求路径
- [ ] 施加测试负载 → 磁盘/网卡/CPU 的 USE 指标序列以预期标签和合理值出现
- [ ] 在追踪 UI 中跨节点、跨副本跟踪了一个请求 → 每个节点一跳，没有断开的 span
- [ ] 制造了一个慢节点 → 离群面板/top-N 查询把它指了出来
- [ ] 一个诱导的故障仅从遥测数据中定位到具体节点/盘，无需登录机器、无需阅读源代码

## 发布前关卡

在组件发布到生产集群之前，以下所有条件均成立：

- [ ] 结构化日志流向日志聚合器，数据面路径有采样
- [ ] 磁盘、网卡、CPU、内存的 USE 指标在仪表盘中可见
- [ ] 至少配置了一个基于症状的告警，附带 runbook，已试触发
- [ ] 一个请求可以在其触及的每个节点/副本中被追踪
- [ ] 值班人员知道 runbook 在哪里，且会跑"找出离群节点"的查询

关于发布日的监控顺序和回滚触发条件，参见 `shipping-and-launch` 技能。
