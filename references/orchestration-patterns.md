# 编排模式

本仓库认可的智能体编排模式参考目录，以及需要避免的反模式。在添加新的协调多个角色的斜杠命令之前，或在引入一个新的"包装"现有角色的角色之前，请阅读本文。

治理规则：**用户（或斜杠命令）是编排者。角色不调用其他角色。** 技能是角色工作流中的必经跳转。

---

## 认可的模式

### 1. 直接调用（无编排）

单一角色、单一视角、单一产物。默认且成本最低的选项。

```
用户 → code-reviewer → 报告 → 用户
```

**何时使用：** 工作是针对单一产物的单一视角评估，你可以用一句话描述它。

**示例：**
- "审查这个 PR" → `code-reviewer`
- "结账流程缺少哪些测试？" → `test-engineer`

**成本：** 一次往返。这是你应始终用来比较编排模式的基线。

---

### 2. 单一角色斜杠命令

一个将单一角色与项目技能包装在一起的斜杠命令。节省用户每次重新解释工作流的时间。

```
/review → code-reviewer（配合 code-review-and-quality 技能）→ 报告
```

**何时使用：** 相同的单一角色调用以相同设置重复发生。

**本仓库中的示例：** `/review`、`/test`、`/code-simplify`。

**成本：** 与直接调用相同。斜杠命令只是一个保存的提示词。

**反信号：** 如果斜杠命令的正文主要是"决定调用哪个角色"，就删除它，让用户直接调用角色。

---

### 3. 并行发散并合并

多个角色同时操作相同的输入，每个产生独立的报告。合并步骤（在主智能体的上下文中）将它们综合为单一决策。

```
                    ┌─→ code-reviewer  ─┐
/ship → 发散  ───┤                   ├─→ 合并 → go/no-go + 回滚
                    └─→ test-engineer  ─┘
```

**何时使用：**
- 子任务是真正独立的（无共享可变状态，无顺序依赖）
- 每个子智能体从自己的上下文窗口中受益
- 合并步骤足够小，能够保持在主上下文中
- 墙钟延迟很重要

**本仓库中的示例：** `/ship`。

**成本：** N 个并行子智能体上下文 + 一个合并轮次。比直接调用高，但墙钟时间更短，并产生更好的报告，因为每个子智能体保持对单一视角的关注。

**采纳此模式前的验证检查清单：**
- [ ] 我能否同时运行所有子智能体而无需担心顺序问题？
- [ ] 每个角色是否产生不同*类型*的发现，而不仅仅是从不同角度产生相同的发现？
- [ ] 合并步骤是否能装入主智能体剩余的上下文中？
- [ ] 用户等待时间是否足够长，使得并行性真正被注意到？

如果任何一个答案是"否"，回退到直接调用或单一角色命令。

---

### 4. 用户驱动的顺序斜杠命令流水线

用户按定义的顺序运行斜杠命令，在它们之间传递上下文（或提交历史）。没有编排智能体——用户就是编排者。

```
用户运行：/spec → /plan → /build → /test → /review → /ship
```

**何时使用：** 工作流有依赖关系（每个步骤需要前一个步骤的输出），步骤之间的人类判断有附加价值。

**本仓库中的示例：** 整个 定义 → 规划 → 构建 → 验证 → 审查 → 发布 生命周期。

**成本：** 每个步骤一个子智能体上下文。编排层免费，因为没有编排智能体。

**为什么不自动化：** 一个 LLM"生命周期编排者"会（a）因为必须总结交接而丢失步骤间的细微差别，（b）跳过那些提早捕获错误方向工作的人员检查点，（c）通过转述轮次使 Token 成本翻倍。

---

### 5. 研究隔离（上下文保护）

当任务需要阅读大量不应污染主上下文的材料时，生成一个研究子智能体，只返回摘要。

```
主智能体 → 研究子智能体（读取 50 个文件）→ 摘要 → 主智能体继续
```

**何时使用：**
- 主会话需要保持对下游任务的关注
- 调查结果远小于其消耗的输入
- 决策质量受益于主智能体在之后有思考空间

**示例：** "在 monorepo 中找到此废弃 API 的所有调用点"，"总结这 30 个 ADR 关于缓存的说法。"

**成本：** 一个隔离的子智能体上下文。任何时候替代方案是向主上下文加载数百个文件时，这都是值得的。

**在 Claude Code 上，使用内置的 `Explore` 子智能体**，而不是定义自定义研究角色。`Explore` 在 Haiku 上运行，被拒绝写入/编辑工具，专为此模式构建。仅在 `Explore` 不适用时才定义自定义研究子智能体（例如你需要一个模型无法推断的领域特定系统提示词）。

## Claude Code 兼容性

此目录与工具框架无关，但大多数读者将在 Claude Code 上运行它。以下是每个模式如何映射到 Claude Code 的原语——以及平台在何处为我们强制执行规则。

### 角色位于何处

插件子智能体放在插件根目录下的 `agents/` 中。此仓库是一个插件（`.claude-plugin/plugin.json`），因此 `agents/code-reviewer.md` 和 `agents/test-engineer.md` 在启用插件时自动发现。无需路径配置。

### 子智能体 vs. Agent Teams

Claude Code 有两个并行原语。模式 3（并行发散并合并）映射到**子智能体**。如果你需要相互通信的团队成员，改用 **Agent Teams**。

| | 子智能体 | Agent Teams |
|--|-----------|-------------|
| 协调 | 主智能体发散，子智能体只回报 | 团队成员互相通信，共享任务列表 |
| 上下文 | 每个子智能体有自己的上下文窗口 | 每个团队成员有自己的上下文窗口 |
| 何时使用 | 产生报告的独立任务 | 需要讨论的协作工作 |
| 状态 | 稳定 | 实验性——需要 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` |
| 成本 | 较低 | 较高——每个团队成员是一个单独的 Claude 实例 |

**本仓库中的角色在两种模式下都能工作。** 当作为子智能体生成时（例如由 `/ship` 生成），它们将发现报告给主会话。当作为团队成员生成时，它们可以直接质疑彼此的发现。角色定义是相同的；只有生成上下文不同。

一个微妙之处：角色中的 `skills` 和 `mcpServers` 前置元数据字段在作为子智能体运行时被遵循，但在作为团队成员运行时**被忽略**——团队成员从你的项目和用户设置中加载技能和 MCP 服务器，与常规会话相同。如果角色依赖于特定的技能或 MCP 服务器被加载，在会话级别配置它，使其在两种模式下都可用。

### 平台强制规则

此目录中的两条规则不仅仅是约定——Claude Code 强制执行它们：

- **"子智能体不能生成其他子智能体"**（逐字来自文档）。反模式 B（角色调用角色）和反模式 D（深层角色树）在 Claude Code 上因构建方式而无法存在。
- **"没有嵌套团队"**——团队成员不能生成自己的团队。相同的反模式在团队级别被阻止。

这意味着你可以采纳此目录中的模式，而不必担心贡献者意外构建反模式。它们根本无法加载。

### 需要了解的内置子智能体

在定义自定义子智能体之前，检查以下是否涵盖该角色：

| 内置 | 用途 |
|----------|---------|
| `Explore` | 只读代码库搜索和分析。用于模式 5（研究隔离）。 |
| `Plan` | 计划模式期间的只读研究。 |
| `general-purpose` | 需要探索和修改的多步骤任务。 |

不要重新定义这些。将你的专业角色（code-reviewer、test-engineer）叠加在它们之上。

### 插件智能体的前置元数据限制

插件子智能体**不**支持 `hooks`、`mcpServers` 或 `permissionMode` 前置元数据字段——这些会被静默忽略。如果未来角色需要这些中的任何一个，用户必须将文件复制到 `.claude/agents/` 或 `~/.claude/agents/` 中。

在插件智能体中确实有效的字段有：`name`、`description`、`tools`、`disallowedTools`、`model`、`maxTurns`、`skills`、`memory`、`background`、`effort`、`isolation`、`color`、`initialPrompt`。如果你想优化成本，按角色使用 `model`（例如 Haiku 用于 `test-engineer` 覆盖率扫描，Sonnet 用于 `code-reviewer`）。

### 并行生成多个子智能体

在 Claude Code 中，并行发散（模式 3）需要在**单个助手回合中发出多个 Agent 工具调用**。顺序回合会序列化执行。`/ship` 明确指出了这一点。任何新的编排命令都应该做同样的事情。

## 示例：使用 Agent Teams 进行竞争假设调试

此示例展示了何时使用 **Agent Teams** 而非 `/ship` 的子智能体发散。两种模式从远处看很相似——两者都生成相同的三个角色——但价值来自不同的地方。

### 场景

> *结账偶尔在完成前挂起约 30 秒。大约每 50 个会话发生一次。日志中没有错误。上周发布后开始出现。*

可能的根本原因（互斥，所有都符合症状）：

1. 新的支付确认流程中的竞争条件
2. 一个认证检查偶尔落入缓慢的同步网络调用
3. 一个随购物车大小缩放的查询缺少索引
4. 一个不稳定的第三方 API，其 SDK 在超时前静默重试

单个智能体会选择第一个看似合理的理论并停止调查。`/ship` 风格的子智能体发散会让每个角色独立报告——但它们的报告永不相遇，所以没有什么能排除错误的理论。

这正是 Agent Teams 文档描述的情况：*"有多个独立调查者积极尝试互相证伪，幸存的理论更可能是真正的根本原因。"*

### 为什么这*不*是 `/ship` 的工作

| | `/ship`（子智能体） | Agent Teams |
|--|--------------------|-------------|
| 子智能体看到 | 相同的 diff，不同的视角 | 共享任务列表，彼此的消息 |
| 输出 | 三个独立报告 → 一次合并 | 对抗性辩论 → 共识根本原因 |
| 适用场景 | 你想要对已知产物的判断 | 你想要在假设中*找到*产物 |

`/ship` 是一个判断；Agent Teams 是一次调查。

### 设置（一次性，每个环境）

Agent Teams 是实验性的。在 `~/.claude/settings.json` 中：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

需要 Claude Code v2.1.32 或更高版本。此仓库中的角色自动被拾取——无需手动编写团队配置文件。

### 触发提示词

用自然语言输入到主导会话中：

```
用户报告结账在上周发布后间歇性挂起约 30 秒。日志中没有错误。

创建一个智能体团队，用竞争假设来调试此问题。使用现有智能体类型生成两个团队成员：

  - code-reviewer  — 调查结账代码路径中的竞争条件和阻塞调用
  - test-engineer  — 提出能区分各假设的测试，并检查结账的覆盖率缺口

让他们直接互相通信以质疑彼此的理论。随着共识出现更新发现。仅当两个团队成员同意他们可以证伪其他人的理论时才收敛。
```

主导生成三个团队成员，引用现有的角色名称。角色正文被**追加**到每个团队成员的系统提示词中作为附加指令（在主导安装的团队协调指令之上）；上面的触发提示词成为他们的任务。

### 发生了什么

1. 每个团队成员在自己的上下文窗口中运行，从自己的视角探索代码库。
2. 团队成员使用 `message` 直接向彼此发送发现。主导不必转述。
3. 共享任务列表显示谁在调查什么——随时可通过 `Ctrl+T`（进程内模式）或在 tmux 窗格中（分屏模式）查看。
4. 当 `code-reviewer` 发现一个应该是顺序的 `Promise.all` 时，它向 `test-engineer` 发消息请求验证该竞争是否会导致可重现的挂起。`test-engineer` 检查并回复——要么确认竞争是真正的问题，要么产生反证。
5. `test-engineer` 为任何领先的理论提出专注的集成测试，团队用它来在宣布共识之前验证。
6. 主导综合收敛的发现并呈现给你。

你可以通过 `Shift+Down` 循环并在任何团队成员处输入来打断——对于重定向走错路径的调查者很有用。

### 何时清理

当调查得出根本原因时，告诉主导：

```
清理团队
```

始终通过主导清理，而不是通过团队成员（根据文档：团队成员缺乏完整团队上下文来进行清理）。

### 成本预期

两个 Sonnet 团队成员运行约 10-15 分钟的调查，成本明显高于由 `/ship` 作为子智能体生成的相同角色。成本合理性的理由是*结论质量*——对于生产调试中错误修复代价高昂的情况，额外的 Token 是划算的。对于常规 PR 审查，坚持使用 `/ship`。

### 此场景中的反模式

**不要**将此重建为发散子智能体的 `/debug` 斜杠命令。子智能体不能相互通信——你会失去使此模式有效的对抗性辩论。如果一个工作流反复出现，将上面的触发提示词记录为代码片段，而不是将其包装在误用子智能体的斜杠命令中。

### 何时*不*使用 Agent Teams

- 对已知 diff 的生产绑定判断 → 使用 `/ship`（子智能体）。
- 针对单一产物的单一专业视角 → 直接调用角色。
- 顺序生命周期（spec → plan → build）→ 用户驱动的斜杠命令（模式 4）。
- 产生小摘要的读取密集型研究 → 内置的 `Explore` 子智能体。

仅当团队成员**需要**互相质疑才能产生正确答案时，才使用 Agent Teams。

## 反模式

### A. 路由器角色（"元编排者"）

一个职责是决定调用哪个其他角色的角色。

```
/work → 路由器角色 → "这需要审查" → code-reviewer → 路由器（转述）→ 用户
```

**为什么失败：**
- 纯粹的路由层，没有领域价值
- 增加了两次转述跳转 → 信息损失 + 约 2 倍 Token 成本
- 用户已经知道他们想要审查；他们可以直接调用 `/review`
- 复制了斜杠命令和 `AGENTS.md` 中的意图映射已经完成的工作

**替代做法：** 添加或改进斜杠命令。在 `AGENTS.md` 中记录意图 → 命令映射。

---

### B. 调用另一个角色的角色

一个在发现测试缺口时内部调用 `test-engineer` 的 `code-reviewer`。

**为什么失败：**
- 角色被设计为产生单一视角；串联它们违背了这一点
- 调用角色传递的摘要丢失了被调用角色所需的上下文
- 失败模式成倍增加（哪个角色的输出格式优先？谁的规则适用？）
- 对用户隐藏了成本

**替代做法：** 让调用角色在其报告中*建议*进行后续审计。用户或斜杠命令运行第二轮。

---

### C. 转述的顺序编排者

一个代表用户调用 `/spec`、然后 `/plan`、然后 `/build` 等的智能体。

**为什么失败：**
- 丢失了捕捉错误方向工作的人员检查点
- 每次交接总结上下文——长流水线中的累积偏差
- Token 成本翻倍：编排者轮次 + 每个步骤的子智能体轮次
- 在最需要判断力的点上移除了用户的主导权

**替代做法：** 让用户保持为编排者。在 `README.md` 中记录推荐的顺序，让用户调用它。

---

### D. 深层角色树

`/ship` 调用 `pre-ship-coordinator`，它调用 `quality-coordinator`，又调用 `code-reviewer`。

**为什么失败：**
- 每个层增加延迟和 Token 而没有决策价值
- 调试变成多层级调查
- 叶节点角色因多次总结步骤而丢失上下文

**替代做法：** 将编排深度保持最多为 1（斜杠命令 → 角色）。合并在主智能体中完成。

---

## 决策流程

在考虑一个新的编排工作流时，按此流程走：

```
工作是针对单一产物的单一视角评估吗？
├── 是 → 直接调用。停止。
└── 否 → 相同的组合会重复出现吗？
         ├── 否 → 直接调用，临时的。停止。
         └── 是 → 子任务是独立的吗？
                  ├── 否 → 用户运行的顺序斜杠命令（模式 4）。
                  └── 是 → 并行发散并合并（模式 3）。
                           对照上面的检查清单验证。
                           如果任何检查失败 → 回退到单一角色命令（模式 2）。
```

## 何时向此目录添加新模式

仅在以下条件之后添加新条目：

1. 你在真实工作中至少使用了两次该模式
2. 你可以指出此仓库中一个具体产物来演示它
3. 你可以解释为什么现有模式不会有效
4. 你可以描述其反模式影子（人们会错误地构建什么来代替）

过早的目录条目会变成没人遵循的愿望文档。
