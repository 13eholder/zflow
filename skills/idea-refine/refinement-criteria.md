# 精炼与评估标准

在阶段 2（评估与收敛）期间使用此评估标准来压力测试想法方向。并非每个标准都适用于每个想法——根据具体上下文判断哪些维度最重要。

## 核心评估维度

### 1. 用户价值

最重要的维度。如果价值不清晰，其他任何东西都不重要。

**止痛药 vs. 维生素：**
- **止痛药：** 解决一个急性的、频繁的问题。用户会主动寻找它。他们会从当前解决方案切换过来。迹象：人们带着情绪描述问题，他们已经构建了变通方案，他们会为解决方案付费。
- **维生素：** 锦上添花。让某些东西边际上更好。用户不会主动寻求。迹象：人们礼貌点头，说"挺酷的"，然后不改变行为。

**要问的问题：**
- 你能说出 3 个现在就有这个问题的具体的人吗？
- 他们今天在做什么替代方案？（真正的竞争对手始终是当前的变通方案。）
- 他们会从当前方法切换吗？什么会使他们切换？
- 他们多久遇到一次这个问题？（日常问题 > 每月问题）
- 这是一个"拉"问题（用户在要求这个）还是一个"推"问题（你认为他们应该想要这个）？

**红旗警告：**
- "每个人都可以用这个"——如果你不能说出一个具体的用户，价值就不清晰
- "它像 X 但更好"——边际改进很少驱动采用
- 问题是真实但不频繁的——高强度但低频率很少证明一个产品是合理的

### 2. 可行性

你能实际构建它吗？不只是在技术上，而是在实际上。

**技术可行性：**
- 核心技术是否存在并可靠工作？
- 最难的技术问题是什么？是已知的难题还是新的难题？
- 是否有对你无法控制的第三方、API 或数据源的依赖？
- 需要的最小技术栈是什么？（如果答案是"很多"，那是一个信号。）

**资源可行性：**
- 构建 MVP 的最小团队/努力是什么？
- 它需要你没有的专业知识吗？
- 是否有监管、法律或合规要求？

**价值实现时间：**
- 你能多快将东西放在用户面前？
- 是否有在几天/几周内提供价值的版本，而非几个月？
- 关键路径是什么？什么必须先发生？

**红旗警告：**
- "我们只需要先解决[非常难的研究问题]"
- 需要同时工作的多个依赖项
- MVP 仍然需要数月的工作——可能不够精简

### 3. 差异化

什么使这个真正不同？不是更好——是*不同*。

**要问的问题：**
- 如果一个用户向朋友描述这个，他们会说什么？那个描述是否引人注目？
- 这个能做什么是其他任何东西做不了的？（如果你不能说出一个，那就是个问题。）
- 这种差异化是持久的吗？竞争对手能在一周内复制吗？
- 差异是用户真正关心的东西，还是只是构建者觉得有趣的东西？

**差异化类型（从最强到最弱）：**
1. **新能力：** 做了以前不可能的事情
2. **10 倍改进：** 在关键维度上如此之好以至改变行为
3. **新受众：** 将现有能力带给被排斥在外的人
4. **新上下文：** 在现有解决方案失败的情境中工作
5. **更好的 UX：** 相同能力，显著更简单的体验
6. **更便宜：** 相同的东西，更低的成本（最弱——容易被竞争淘汰）

**红旗警告：**
- 差异化完全关于技术，而非用户体验
- "我们更快/更便宜/更漂亮"而没有结构性的原因说明为什么
- 差异化的功能不是用户最关心的功能

## 假设审计

对于每个想法方向，显式列出三类假设：

### 必须为真（交易破坏者）
如果错误的假设会完全扼杀想法。这些需要在构建之前验证。

示例："用户将与我们一起分享数据"——如果他们不分享，整个产品无法工作。

### 应该为真（重要）
假设会显著影响成功但不会扼杀想法。如果这些是错的，你可以调整方法。

示例："用户更喜欢自助服务而非与人交谈"——如果错误，你需要不同的市场进入策略，但核心产品仍然可以工作。

### 可能为真（锦上添花）
关于次要功能或优化的假设。在核心被证明之前不要验证这些。

示例："用户会想要与队友分享他们的结果"——一个增长功能，而非核心价值主张。

## 决策框架

在方向之间选择时，按此矩阵排名：

|                    | 高可行性 | 低可行性 |
|--------------------|-------------------|-----------------|
| **高价值**         | 优先做这个         | 值得冒风险       |
| **低价值**         | 仅当微不足道时才做 | 不要做这个       |

然后使用差异化作为同一象限中选项之间的决胜因素。

## MVP 范围界定原则

为选定方向定义 MVP 范围时：

1. **一件工作，做得很好。** MVP 应该精确地完成一个用户工作。不是三件部分完成的工作。
2. **最有风险的假设优先。** MVP 的主要目的是测试最可能为错的假设。
3. **限定时间，而非功能列表。** "我们能在[时间范围]内构建和测试什么？"比"我们需要什么功能？"更好。
4. **"不做什么"列表是强制的。** 显式说出你砍掉了什么以及为什么。这可以防止范围蠕变并迫使诚实的优先级排序。
5. **如果它不令人尴尬，你就等太久了。** 第一个版本对构建者来说应该感觉不完整。如果不感觉不完整，你过度构建了。
