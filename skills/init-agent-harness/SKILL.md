# 初始化 Agent Harness

## 概述

在项目开始阶段执行一次，将仓库已有知识整理为简短入口、按任务导航和可追溯的专题文档。使后续智能体能找到适用约束，并随代码变更维护对应文档。

必须调查设计文档、编程规范、架构设计、模块依赖、错误处理、测试原则、命名规范与提交约定八类知识。初始化交付的是基于仓库证据的文档基线；知识缺口和冲突必须显式保留。

## 何时使用

仅允许用户显式指定调用 `init-agent-harness`（例如 `$init-agent-harness` 或“使用 init-agent-harness”）。智能体不得依据项目刚开始、文档缺失或入口冗长而主动调用，也不得由其他技能自动串联调用。

用户指定调用后，用于首次整理工程约定与渐进式文档入口；再次指定调用时，补缺和校准已有基线。

日常开发直接维护已有文档，无需重复调用本技能。单份文档或 ADR 的写作使用 `documentation-and-adrs`；本技能不自动创建 Stage、实施计划或新的架构决策。

## 流程

### 1. 盘点现有依据

确认目标仓库和工作区已有变更。先列文件，再按主题读取：

- 根目录与相关子目录的智能体指令、README、贡献指南、文档索引。
- 设计文档、已接受 ADR、架构图、接口定义和现有规范。
- 构建清单、依赖配置、格式化与静态检查配置、CI、测试入口。
- 与关键模块边界、错误路径、测试方式对应的代表性源码。

新建知识文档统一放在 `.agents/context/`，沿用目标项目的语言和文档格式。已有权威文档保留原路径，通过 AGENTS.md 导航引用，避免复制或擅自迁移。不得把本技能所在仓库的 AGENTS.md 或工程政策复制到目标项目。嵌套指令的适用范围需要保留，不能把局部规则提升为全局规则。

### 2. 提取八类知识

逐项完成“主题 → 文档位置 → 依据 → 状态”的调查，覆盖情况随交付报告，不单独落盘为覆盖表文件；缺口与冲突在对应专题文档内以“待确认”“存在冲突”显式标注。

| 主题 | 必须调查的内容 | 优先查阅的依据 |
|---|---|---|
| 设计文档 | 项目目标、需求、关键约束、设计取舍、已接受决策 | 设计说明、Spec、ADR、接口契约 |
| 编程规范 | 代码风格、注释风格、接口约定、资源管理、并发与 ownership 规则 | 贡献指南、lint 配置、代表性实现与注释 |
| 架构设计 | 系统边界、分层、组件职责、核心数据流 | 架构说明、入口代码、组件实现 |
| 模块依赖 | 依赖方向、允许和禁止的依赖、跨模块访问边界 | 构建清单、导入关系、架构约束 |
| 错误处理 | 错误类型、传播与转换、重试条件、日志责任、panic／异常边界 | 错误定义、调用链、故障测试 |
| 测试原则 | 测试分层、隔离性、确定性、故障场景、执行方式、验收要求 | 测试目录、测试指南、CI |
| 命名规范 | 文件、模块、类型、函数、变量与测试用例命名 | 明文规范、lint 配置、跨模块样本 |
| 提交约定 | Git 提交信息格式、分支与合并流程 | 贡献指南、commit 历史、CI 配置 |

区分四种状态，必要时在同一主题内逐条标注：

- **已确立规范**：有明确规则或已接受决策，引用其权威位置。
- **现有实践**：从实现或配置观察到的模式，注明样本和适用范围；不能直接升级为强制规则。
- **待确认**：缺少证据，记录具体问题及确认所需材料，不编造默认答案。
- **存在冲突**：并列列出来源与差异；区分规范要求和当前实现，不自行修改系统承诺来消除差异。

八类主题都必须有调查结果。空仓库也应记录缺口；缺失知识不妨碍整理已有证据，但必须报告基线尚不完整。只有会改变既有规则含义的冲突需要用户决定，其他独立整理继续进行。

对于 Rust/C++ 项目，尤其检查所有权与生命周期、锁顺序、unsafe／FFI 边界、Result／异常传播等已有约定；语言惯例本身不能证明项目采用了某条政策。依赖清单只证明声明依赖，允许和禁止的架构边界仍需规范依据。

### 3. 建立渐进式披露结构

入口层由根 AGENTS.md 独自承担，专题层承载完整规则，来源层链接源码、配置、测试和决策记录。

文档根目录固定为 `.agents/context/`，按知识性质分为两个子目录：`convention/` 存放项目约定，即可以被一次提交违反的规则；`arch/` 存放系统事实，即系统是什么和为什么这样设计。已有等价文档时直接引用并补齐缺口；每条规则选择一个权威维护位置。目录按以下职责划分：

```text
AGENTS.md                         # 渐进式披露地图：项目定位、全局约束、代码导航表格、维护约定
.agents/context/
├── convention/                   # 项目约定：可被一次提交违反的规则
│   ├── code-style.md             # 代码风格与注释风格
│   ├── naming.md                 # 文件、模块、类型、函数与测试命名
│   ├── interfaces.md             # 模块接口与依赖边界
│   ├── error-handling.md         # 错误传播、转换、重试与日志责任
│   ├── testing.md                # 测试原则、用例命名、命令与验收
│   └── git-conventions.md        # 提交信息、分支与合并约定
└── arch/                         # 系统事实：架构、设计与决策
    ├── architecture.md           # 架构、组件职责、数据流、依赖方向
    ├── design-docs/              # 设计文档、已接受决策与需求契约
    └── tech-debt.md              # 已知技术债务
```

模块依赖跨两侧：依赖边界规则归 `convention/interfaces.md`，依赖方向与结构依据归 `arch/architecture.md`，两侧互相链接。

八类知识必须完整落位到上述专题或既有权威文档；专题文件按实际证据创建，缺少资料时在交付清单记录待确认项。design-docs 与技术债务文件按需创建。初始化不创建执行计划；项目已有相关资料时通过导航引用原位置。前端、可靠性、安全、质量评分等专题在项目确有资料时再增加。外部资料不设专门目录，由引用它的专题文档直接链接原始来源。

根 AGENTS.md 承担唯一入口职责，包含四个部分：项目定位、适用于所有任务的必要约束、代码导航章节、维护约定（见第 4 步）。代码导航章节使用两列表格，读取条件描述触发场景，链接指向 `.agents/context/` 专题文档或既有权威文档，例如：

| 读取条件 | 链接 |
|---|---|
| 修改跨模块调用或新增依赖时 | convention/interfaces.md 的依赖边界章节 |
| 新增错误分支或重试逻辑时 | convention/error-handling.md |
| 调整组件职责或系统边界时 | arch/architecture.md |

仅要求读取当前任务涉及的专题，不要求预先通读整个知识库。AGENTS.md 以约 100 行以内为参考，优先保留约束完整性；不为凑行数删除规则。

迁移既有规则时检查旧引用、相对链接和适用范围，保留可达入口。若项目已有其他智能体入口，沿用实际入口并链接同一套知识，不制造多份政策副本。

### 4. 建立维护约定

在 AGENTS.md 尾部或既有贡献指南中明确：修改接口、依赖、错误语义、测试方式、注释或提交约定等内容时，同步更新其权威文档；移动文档时更新代码导航表格和引用。已接受 ADR 的历史保留，替代决策沿用项目既有流程。

为新整理的主题记录来源和核验状态；已有 owner 时沿用，无法确定时标记待确认。时间戳只能表示检查时间，不能代替事实核验。生成文档引用生成入口，避免手工改写派生内容。

优先使用已有文档检查命令。没有自动检查时完成链接与内容核验，并说明当前检查方式；未经本次任务要求，不引入 CI、定时任务或外部服务。

### 5. 验证与交付

核对八类调查记录，检查本次新增或修改文档的本地链接与章节锚点。抽查规则引用能否支持对应陈述；对构建和测试命令记录工作目录、前置条件、配置来源与实际执行状态。未运行的命令不得标记为验证通过。

选择两个符合项目实际的任务，如“修改模块间调用”“新增错误分支和回归测试”，从 AGENTS.md 代码导航表格沿链接查找相关约束，记录路径和结果。确认无需读取无关专题即可定位所需知识；找不到的约束回填为明确缺口。

检查 diff 中原有规则是否保留、是否引入重复来源。再次评估相同输入：已有有效内容应被复用，不重建目录、不重复插入导航、不仅为刷新日期改写文件。

交付修改文件清单、八类覆盖情况、检查结果及待确认项。区分“初始化结构已完成”和“所有知识已确认”；存在缺口时给出具体范围。

## 常见合理化借口

| 合理化借口 | 处理原则 |
|---|---|
| “先套一套完整目录，以后填内容” | 依据仓库知识创建必要文档，八类缺口集中记录即可。 |
| “代码都是这么写的，就定为规范” | 实现样本是现有实践，强制约束需要明确依据。 |
| “缩短入口可以删掉冷门约束” | 将详细约束移到可达专题，保持原有含义与适用范围。 |
| “链接检查通过就完成了” | 还要验证导航能找到任务约束，以及来源支持文档结论。 |

## 红旗警告

- 八类主题有遗漏，或以空标题代替调查结果。
- 从目录名推断架构、从依赖存在推断依赖许可、从单个测试推断完整测试政策。
- 把未经验证的重试、持久性或错误转换行为写成系统保证。
- 默认让每个任务加载全部文档，或把长篇规则复制到多个入口。
- 重跑产生平行文档体系，或擅自覆盖用户已有改动。

## 验证

- [ ] 本次调用由用户显式指定，未通过任务推断或技能串联主动触发。
- [ ] 新建知识文档位于 `.agents/context/` 的 convention/ 或 arch/，AGENTS.md 代码导航表格可达。
- [ ] 八类主题均有位置、依据与状态，缺口和冲突在专题文档内可定位。
- [ ] 原有约束语义、局部作用域与历史决策得到保留。
- [ ] 每条规则有唯一权威位置，代码导航表格的读取条件明确。
- [ ] 本次涉及的链接、锚点及命令来源已核验，执行状态如实记录。
- [ ] 两个实际任务的导航走查有路径和结果。
- [ ] 相同输入下重复运行不会重复生成或无意义改写。
- [ ] 后续变更的文档同步责任已记录，未确认项在交付中明确列出。

## 设计依据

[OpenAI：Harness engineering](https://openai.com/zh-Hans-CN/index/harness-engineering/) 提供了简短入口、仓库知识库和渐进式披露的实践依据。八类必查主题与上述初始化验收要求是本技能的项目约定。
